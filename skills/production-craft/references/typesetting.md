# 精确排字

将给定文字和字体关系可重复地落实到成品。保持准确文案、阅读层级和含义；没有授权时不换方向、不改字、不通过不可读缩小来省事。

## 核对文本与字体

使用当前准确文本，确认字符、标点、简繁和语言变体。核对姓名、数字、日期、版本、单位、否定与限定，以及必要来源和说明。留意视觉相近却不相同的字符、不可见字符或错误换行；不要自动归一化会改变语义的内容。

程序核验逐字一致时，明确比较的是原始编码、Unicode 码点还是规范等价文本；语言运行时的字符串相等可能接受不同码点序列。保留准确源文，不能以自动归一化或重排后的相等冒充原文完全一致。

确认字体实际存在、适合当前用途且覆盖所需中文字形、拉丁文、数字、符号或代码。检查目标渲染环境和后备字体。缺字可能触发局部替换，不能因文件成功导出就认为整段使用同一字体。

可重复排字需识别实际字体文件／版本、字重或可变轴，以及影响结果的排版引擎、语言、方向与 OpenType 功能。只记录会影响重建的条件，不要求每次写环境清单。字符覆盖表只能筛查部分缺字，不能证明字形选择、组合或回退正确；在实际渲染中复核。文档嵌入与原始字体文件再分发的许可不同，交源文件时不能自动打包未获准分发的字体。

需要诊断或重现回退时，读取成形后各文字段实际解析到的字体，不能只抄文本框请求的字体名。回退可能改变字宽、行高和字形关系；核对受影响的断行、基线与可见外框。已符合要求的回退可以保留，不要求为统一字体名而换字形。

## 落实字体角色

按已有设计或本次明确要求实现字体与后备、字重字宽、字号／响应行为、行距字距、对齐、行长断行、明暗、层次、最低可读条件和变体。已有清楚规格就直接实施，不重新做字体选秀。

断行保持词组、姓名、数字单位、限定及修辞关系。中文检查不当行首行尾标点、孤立短尾行、引号和地区字形；英文检查断词、词距、孤行与连字。文本不适配时先尝试许可范围内的栏宽、行距或布局调整；内容或设计决定需要改变时明确提出具体冲突。

## 让测量与绘制使用同一排版条件

自动排版以实际成形后的字形前进量和位置测宽，不用字符数乘字号或逐码点累加作为最终宽度。连字、组合附标、字偶距、双向文字和回退可能改变结果；需要这些功能时用确实支持它们的引擎，不把简单横排的测试推广为所有文字系统已通过。改变文案、字体、语言、栏宽或回退后，重新排版受影响范围。

需要自行绘制字形时，保留引擎给出的实际位置、偏移、变换与方向；只有前进量不足以重建附标定位和复杂文字。字形顺序与源文索引可能不单调，不按视觉顺序反写源文，也不把每个字形当成一个字符。

分清可断行位置、实际选用的断行与字形成形。不要截断组合字符或连接序列来硬塞文字；换行后的上下文可能需要重新成形。[Unicode UAX #14](https://www.unicode.org/reports/tr14/) 给出断行机会，不替排版系统决定最终行宽；[HarfBuzz 的 cluster](https://harfbuzz.github.io/working-with-harfbuzz-clusters.html) 关联输入与字形，也不等于语言允许的换行点。锁定的标题断行可保留，不要求全部自动重排。

受限文本框或多框续排时，检查实际排入的源文范围与未排入的尾文；框内没有明显裁切也可能已经漏行。续排索引使用引擎规定的单位，例如 CoreText 的字符串范围使用 UTF-16，不能混用字素数量、码点数量和编码单元。检查总文案是否排完，再检查实际字形是否越界；扩大框、改变栏宽或修改源文后重查两者。

前进量用于安排后续文字，字形实际外框用于判断是否被裁；斜体、重音、描边与阴影可能伸出前进量或行框。同时检查文本框、祖先遮罩／裁切和页面边界，避免“宽度放得下”但可见笔画被切掉。最终仍看实际渲染，字体度量不是光学对齐或可读性的代替品。

## 光学与图像检查

实际看标点边空、悬挂对齐、CJK／拉丁表观大小、基线、大写高度、字形不对称、视觉居中和重复角色。相同字号和数学居中不是最终正确性的证明。

在完整页面中检查背景局部对比、遮罩、重叠和字形识别，同时保护人脸、动作、界面及证据。多语言文字量和字形不同，各变体需单独检查适配，不强行复制断行。

## 核对导出结果

打开或渲染实际导出文件，对照准确文本和设计检查字形、断行、标点、数字、限定、层级、位置及裁切。源文件里的正确设置不能证明导出正确。

可提取文字时用文本比较帮助发现遗漏；提取结果不证明视觉可读。OCR 可辅助发现疑点，不单独证明逐字准确，尤其是装饰字、混排和小字。不能提取时逐项目视核对关键文字，并如实说明检查范围。

复杂文字的源文逻辑顺序、画面上的字形顺序与 PDF 提取结果可能不同。发现替代字符、附标错序或双向混排差异时，分别检查源文、成形结果和导出的文字映射；必要时用另一种提取器定位差异，不为让某个比较器通过而倒序源文或改掉正确字形。需要搜索、复制或辅助阅读时，在相应阅读环境实测；嵌入字体不保证文字映射正确，ToUnicode 或 ActualText 的存在也不等于复制结果或无障碍合规已通过。静态栅格交付无需因此强加 PDF 文本层。

具体诊断 PDF 映射时，追踪实际字体资源对象和绘制字符码，分别检查字形选择、ToUnicode 及覆盖该绘制范围的 ActualText。字符码与字形编号角色不同，不能默认数值相同；提取器可能忽略已有的准确替代文字，不能只看低层映射就断言原文丢失。按目标读取环境决定是否需要兼容修复，保留已有正确语义。

修改共享字体映射前，核对受影响码在各页及复用内容中的全部用途，依据准确源文与实际位置确认字符身份。相同字形甚至同一码可能承载不同源字符，不能靠字体反查或全局归一化猜回原文。一个码可映射为有依据的字符序列，但这不负责跨码的逻辑重排；有身份冲突时需保留位置上的区分或回到源端生成，不随意合并。相关机制见 [PDF 规范的文字提取与替代文本章节](https://opensource.adobe.com/dc-acrobat-sdk-docs/standards/pdfstandards/pdf/PDF32000_2008.pdf)（§9.10、§14.9.4）。

字体替换、缺字或语言不适配修正后重新导出并检查新文件。保留实际检查证据到本次项目，不宣称未查看的文件已经无误。

原生 CoreText 排字的具体依据可查 [Apple Core Text 编程指南](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/CoreText_Programming/Overview/Overview.html)；字符串比较的差异见 [Swift 字符串与字符](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/stringsandcharacters/)。这些是实现路径的例子，不要求其他排版工具迁移到此环境。
