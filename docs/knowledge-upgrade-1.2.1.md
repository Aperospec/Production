# 1.2.1-alpha: PDF mapping diagnosis and bounded repair

This increment adds two concrete actions to typography diagnosis: trace the actual font resource, content code and covering ActualText span; check every use of an affected shared mapping against exact source identity before changing it. Export checks now assess the version declaration against retained features. No particular extractor, sample language, repair script or PDF version becomes a package default.

The existing two-page complex-text specimen already contained accurate inline ActualText. This explains the earlier unsuccessful extra-tag experiment: adding replacement text did not address the observed reader path. Inspection of pypdf 6.10.0 and Poppler 26.05.0 source, together with their actual output, showed that the tested pypdf default path ignored those spans while Poppler consumed them. Apple PDFKit supplied a third observed extraction result; its internal implementation was not inferred.

A bounded derivative corrected one Chinese ToUnicode entry and filled nine missing Devanagari entries. Exact source ranges, actual content codes, embedded font tables and every occurrence supported these changes. The Chinese character then extracted correctly in pypdf, and missing Devanagari codes stopped falling back to unrelated ASCII in pypdf and PDFKit. Devanagari logical order remained wrong in their whole-string output: independent per-code mappings cannot reorder separate content codes. Poppler output was unchanged because the original replacement text already worked there.

Both rendered pages had zero changed pixels at the tested resolution. Decoded drawing streams, all seven embedded font streams, page geometry, existing ActualText and relevant metadata were preserved. The inherited PDF 1.3 declaration did not reflect the existing marked-content ActualText feature; the derivative declares 1.5. A header-only control changed no reader output or rendered pixels. This corrects the earlier assumption that retaining the old header was sufficient; it is not a full PDF conformance assessment.

A new source containing both ordinary U+884C and radical U+2F8F produced the same font code for the two intended characters. Existing local ActualText preserved their distinction for two tested readers; a global ToUnicode replacement could not preserve both for a reader ignoring that layer. That counterexample rules out blind font reversal or blanket Unicode normalization as a repair method.

Original files, raw extraction failures, occurrence-level research, repaired derivatives, renders and independent review remain in local maintenance evidence, outside the installed package and distribution history. This is measured extraction compatibility on bounded specimens, not universal copying, language-reader approval, accessibility certification, device rendering or print validation.
